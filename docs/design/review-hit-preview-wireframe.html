Hearing the hit before you exclude it

A working prototype of the proposed Review-step addition: select a hit, hear exactly the padded window that render would silence, decide with your ears instead of just the transcript's text. Reuses the base app's own AudioPlayerWidget — no new playback engine.

Plan at a glance

New data into Review
The source .m4b path — ReviewStep.set_scan() gains a source_path argument, wired from SourceStep.manifest the same way Render already reads it.
What gets played
Two toggleable windows, same clip: Filtered word (start_ms − lead_padding_ms to end_ms + tail_padding_ms — what Render actually silences) or Word in context (a plain fixed ±2s either side, for "is this really the flagged word").
New capability
AudioPlayerWidget.play_clip(path, start_ms, end_ms) — plays and auto-pauses at end_ms. One small, generically useful addition to the shared widget, not a filter-only fork of it.
Interaction
Click a row → loads paused at the clip start (mirrors the base app's own chapter-preview pattern exactly). Press ▶ → plays the clip, auto-stops at the end.
Where it lives
A slim row docked directly under the Hits table (~44px, idle or loaded) — not a third tab. Mirrors the base app's own Chapters-tab AudioPlayerWidget placement exactly, not a new convention.

Try it below — click any row, then press play. Selecting a different row while one is playing swaps the clip immediately; selecting zero or several rows disables preview.

Trade-offs worth flagging

  • Two windows, one player, no new data. "Filtered word" answers "will this cut off too much / too little"; "Word in context" answers "is this really the flagged word." Both are plain ±ms arithmetic on the hit's own start_ms/end_ms — no transcript word-index lookup needed for either. Labels named for what a User recognizes ("filtered," this app's own name) rather than the mechanism ("padded," "lead-in") — see FORK.md/ADR notes once this is built.
  • Fixed seconds over word-count boundaries. A first pass considered sizing the context window to N real transcript words either side (exact, but needs new data exposed from TranscriptWordIndex). Rejected: audiobook narration paces steadily enough that ±2s already reads as "a few words" in practice, and word-count boundaries don't avoid crossing a chapter break any better than fixed seconds do — not enough upside for the extra surface area.
  • The scrub position is real-file-absolute, not clip-relative. Embedding the actual AudioPlayerWidget means its slider still spans the whole book, not just the active clip — accepted for v1 rather than teaching the shared widget a new "bounded range" mode.
  • Extending the shared widget, not forking it. play_clip() lives on AudioPlayerWidget itself, in the base app's own module — a small, generically useful capability (any future "preview a clip" need benefits), not a filter-only reimplementation of position tracking.
  • No separate Stop button. The base AudioPlayerWidget has one, because resuming a multi-hour book from exactly where you paused is genuinely worth a dedicated control. These clips run a few seconds — resuming mid-clip isn't worth much, so ▶/⏸ mid-playback just halts and resets to the clip's own start, same as letting it finish naturally already does. One button, one way to "stop": back to the top.
  • The label is elided, the tooltip has the rest. Caught in review: a long catalog phrase (no length cap in the data model) plus the full clock range could push the mode toggle/progress/time off the row entirely — confirmed in the mockup itself before fixing it. Same convention source_step.py's _InfoPanel already uses: a fixed-width elide on the visible text, full detail in the tooltip, nothing ever grows past its budget. The inline label now shows only the term; the exact clock range + lead-in/tail (or before/after) explanation lives in its tooltip, since the time readout beside it already shows duration. Verified against the wizard's own real minimum window size (760×560, wizard_window.py), not just this document's own wider layout.
  • Not shown here: multi-select behavior (existing bulk Include/Exclude is untouched — preview is single-hit only), and stopping playback on navigating away from Review (hideEvent override, no shell changes needed).
  • A third "Player" tab was considered and dropped. It would keep the Hits table maximally uncluttered, but it breaks the one thing this feature is for — hearing the audio while looking at the Context column and Include checkbox — into two screens, adds a click every single time, and does nothing for the Render Plan tab. A slim docked row costs one row of table height and needs no new tab content at all; the base app already proves this exact placement works (Chapters tab, gui/window.py) for the same "big table + occasional audio" shape.

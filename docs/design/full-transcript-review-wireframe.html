Filter feature · ADR-0053, Option 1 · planning draft, not yet an ADR

Reading what the scan didn't flag

A new Review-step tab: the whole chapter, hits already struck through, everything else there to actually read. Select any other word or phrase to hear it or add it straight to the catalog — the one approach ADR-0053's real-data testing found that doesn't depend on an algorithm correctly guessing what to flag.

Plan at a glance

New data into Review
Nothing new — Transcript.words() and the real ScanHit list are already both in memory for this step; this tab is a different view over data the app already has.
Navigation
Paginated by chapter (the transcript's own segments are already roughly chapter-aligned — no new data needed), plus a "Jump to next hit" button so a hit-dense chapter doesn't need reading word-by-word around parts already verified.
Selecting text
Click a word, or drag across several — the same gesture as selecting text anywhere else. A drag stops at a hit's edge rather than trying to span across one.
Acting on a selection
A persistent "＋ Add to Catalog" control (enabled only with a selection, same pattern the Hits-tab preview dock already uses) and a right-click "Add… to Catalog" menu item on the same selection — two paths to the same action.
Listening first
Reuses ADR-0052's preview player — select, then press play to hear exactly that span before deciding to add it.
What "Add" actually does
Catalog only, not the current scan. Review's own hits are matched against an "immutable profile snapshot" — adding a word here doesn't retroactively create hits for every other occurrence in this book. A visible banner tracks how many entries were added this session and prompts a re-scan, rather than pretending the fix is already fully applied.
Signaling it's optional
The tab opens last in the row (after Render Plan, not competing with Hits), carries a tooltip on hover before anyone even clicks in, and its own note says outright that most people won't need it — same wording pattern ADR-0045 already used for the Render Plan tab's own "most people won't need to check this" note. No "NEW" badge — that invites clicking, the opposite of what's wanted here.

Try it below — opens on Hits, same as the real app would. Click "Transcript" to see the new tab; drag or click a word to select it, press ▶ to hear it, or ＋ to add it (or right-click a selection to do the same). Trade-offs worth flagging

  • Word-span selection, not native text selection. Each word is its own clickable unit (click one, drag across several) rather than free-form character selection — simpler to snap cleanly to whole words every time, at the cost of not being able to select a partial word (never a real need here) or start a selection mid-hit.
  • A drag can't cross into a hit. Extending a selection stops at a hit's edge rather than spanning over it — keeps "what you're about to add" unambiguous, since a hit is already handled and has no reason to be part of a new addition.
  • "Add" changes the catalog, not this session's hits — and says so. The alternative (re-masking the word live, everywhere, without a real scan) would feel more responsive but would misrepresent what actually happened: "Total hits" and the render plan wouldn't reflect it until a real re-scan runs. The banner exists specifically so that gap is never silently assumed away.
  • Single preview mode, same reasoning ADR-0052's own dock already established. A word that isn't in the catalog yet has no padding window to toggle to — one fixed-span playback, not two.
  • "Highlight uncertain words" is an unverified idea, not a validated feature. ADR-0053's real-data testing rejected confidence as a filter (Option 4) — it produced thousands of candidates with no genuine signal. This is a different, much smaller claim: used only as a visual hint while every word is already shown anyway, it might draw the eye usefully. Shown here toggleable, and off by default would be the more defensible starting point given it's never actually been tested — on here mainly so the trade-off itself is visible to evaluate.
  • Chapter pagination is real, chapter content isn't. The dropdown and Prev/Next buttons are shown as real UI elements to evaluate their presence and labels; clicking between chapters doesn't load different real text in this mockup — that's a data-plumbing question, not the interaction question this draft is for.
  • Right-click is a shortcut, not a separate feature. It fires the exact same add-flow as the persistent button — included because some people reach for it instinctively, not as a second thing to maintain.
  • Optional, and shown as such, not just claimed as such. Every inactive tab in this app's real tab bar already renders identically muted — there's no "extra muted" style to reach for, so the signal comes from order (last, after Render Plan, not interrupting Hits → Render Plan → Continue), an on-hover tooltip before anyone clicks in, and an in-tab note stating plainly that most people won't need this — reusing ADR-0045's exact wording pattern for the same problem, not a new convention. No "NEW" badge in the real build: that invites checking, which is backwards from the goal. The mockup now opens on Hits by default, same as the real app would, rather than jumping straight to the tab being demonstrated.
